The bridge between HTTP and the decentralized web.

A gateway listens for requests for content by identifier, retrieves that content, verifies it against the identifier, and serves it over ordinary HTTP to any browser. Everything on this page is talking to a real gateway running on your machine — real SHA-256 CIDs, real verification, real 410 Gone responses.

02

Publish a block

Content is addressed on write, not on lookup: the gateway hashes what you give it and hands back the address. Publish the same bytes twice and the address does not change.

04

Abuse, takedown and the denylist

A gateway is a public utility, so it has to answer for what it serves. Reporting a CID puts it through review; a takedown decision adds the identifier to the denylist, and the gateway then answers 410 Gone for it while the content itself stays untouched on the network.

1

Report

Submit the CID or URL and the reason, by web form or email to abuse@ipfs.io.

2

Receipt

An automated system receipt is issued so the report can be tracked.

3

Review

The takedown team checks the request is legitimate against the acceptable use policy. Copyright claims need full DMCA detail.

4

Denylist

A confirmed takedown adds the identifier to the public Bad Bits denylist.

5

410 Gone

Gateways refuse the content. Your browser's local cache may still hold it — use a private window or curl.

Denylist mirror (local)

On a real gateway the entry is written to badbits.dwebops.pub and every participating gateway refuses the CID. Here the mirror is a local JSON file, so the behaviour is identical but the scope is this one process.

05

How it works

addressing

The address is the hash

A CIDv1 here is version 1, raw codec 0x55, sha2-256 multihash 0x12 0x20 plus 32 digest bytes, base32-encoded with a b prefix. Same bytes, same CID, on any machine.

gateway

HTTP in, blocks out

The gateway speaks HTTP so any browser can reach the content, and speaks block retrieval underneath. It is a bridge, and an interim one: the longer-term goal is direct ipfs:// support in browsers.

verification

Trust, then verify

Every block is re-hashed before it leaves. Tamper with a block and the gateway returns 502 instead of the bytes. Clients can also request the raw block and verify the CID themselves.

immutability

Content never changes

Because the CID covers the bytes, a block is safe to cache forever. Responses carry ETag and a year-long immutable Cache-Control.

directories

Sites are link manifests

A directory is a block whose JSON body maps names to CIDs. Paths resolve by walking those links, so a whole site has one root CID and every file keeps its own.

refusal

Takedown is local

Denylisting does not delete anything. It makes one gateway decline to serve an identifier — which is exactly the authority a gateway actually has.

Acceptable use

The content is uploaded by third parties, and the person using it carries the consequences of doing so. Content that violates the policy may be removed or disabled immediately, without compensation, by adding its identifier to the denylist.

07

Operational notes

What this build is not

No libp2p, no DHT, no bitswap, no dag-pb or UnixFS, no pinning. Blocks sit on local disk and directories are JSON link manifests, so a real ipfs add of the same bytes yields a different CID. The addressing, verification, HTTP surface and takedown semantics are the parts that carry over.

Limits on the public gateways

Range requests are capped at 5 GiB (a CDN restriction); larger files come back as a full 200. Public gateways are free, as-is, and not meant to sit in a production critical path. Support runs through the IPFS forum.
